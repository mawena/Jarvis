# Jarvis, phase 3 (voix de Jarvis) : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** Jarvis répond à voix haute, en français, sur l'oreille qui l'a entendu ; un petit son confirme « Jarvis », la réussite ou l'échec ; les actions risquées attendent un « oui » dit dans les 8 s sur la même oreille ; « annule » et « répète » marchent ; le ton est bref et majordome.

**Architecture :** le **cerveau** synthétise la voix (Piper, local dans les deux modes, spec §5.3 étape 6) et renvoie le son dans la réponse `Heard` ; l'**oreille** joue le son (et ses propres bips) et peut être interrompue. En phase 4, le même message passera sur WebSocket : l'audio voyage donc dans le protocole, pas par un lecteur côté cerveau. La confirmation est un état du cerveau (une action en attente, 8 s) ; l'oreille rouvre une écoute **sans mot d'éveil** quand le cerveau le demande.

**Tech Stack :** sherpa-onnx 2.0.1 (déjà lié en `shared` pour l'empreinte vocale) pour la synthèse Piper/VITS ; lecture par la sortie `cpal` 0.18 de l'oreille ; bips générés en Rust. Existant : tokio, serde, base64, tracing.

**Spec :** [docs/superpowers/specs/2026-10-28-jarvis-design.md](../specs/2026-10-28-jarvis-design.md) (§5.3, §5.6, §6.5, §8)

## Global Constraints

- Synthèse **locale dans les deux modes**, hors du runtime (`spawn_blocking`). Si la voix n'est pas installée ou échoue, le cerveau répond quand même (texte seul, avertissement journalisé) : la voix ne bloque jamais une action.
- Le son de la réponse est en i16 little-endian mono, base64, avec sa fréquence (`sample_rate`) : l'oreille rééchantillonne vers sa sortie.
- L'oreille ne s'entend pas elle-même : pendant la lecture, la phrase suivante n'est captée qu'après « Jarvis » (le mot d'éveil reste actif et **coupe** la lecture en cours).
- Actions risquées (spec §5.6) : rien n'est exécuté sans un « oui » de la voix de Charles (vérification du locuteur comprise) dans les 8 s ; sans réponse, ou toute autre réponse, rien n'est fait. Une seule action en attente à la fois ; une nouvelle commande l'annule.
- Aucun son n'est enregistré sur disque. Le texte dit par Jarvis est journalisé en `debug` seulement.
- Personnalité (§8) : réponses brèves, vouvoiement, nom d'adresse configurable (`address`, déjà présent). Option `sound_only_for_success` : une action anodine réussie peut être confirmée par un bip au lieu d'une phrase.
- Les règles des phases précédentes restent valables (git flow, commits au nom de Charles sans attribution, `ROADMAP.md` coché dès qu'une tâche est validée, `scripts/check.sh` vert, jamais `cargo update` sans `-p`, ne pas redémarrer le service ni ouvrir le micro sans Charles).

## Review Focus

1. **Voix absente ou en panne** : la commande s'exécute et la réponse texte arrive. → test `synthese_en_echec_reponse_sans_audio` (tâche 2).
2. **Confirmation** : une action risquée n'est jamais exécutée sans « oui » ; délai de 8 s dépassé, « non », autre phrase ou voix inconnue → rien. → tests de la tâche 4.
3. **« Jarvis » pendant que Jarvis parle** : la lecture s'arrête, la nouvelle phrase est captée. → test `reveil_coupe_la_lecture` (tâche 3).
4. **Compatibilité** : un ancien client (sans les nouveaux champs) reste compris. → tests serde de la tâche 1.

## Choix de la voix

Mesuré le 2026-10-28 sur le PC de Charles (machine chargée par des compilations, chiffres au mieux de 3 essais) :

| voix | genre | fréquence | « Bien, monsieur. » | phrase longue | licence |
|---|---|---|---|---|---|
| **upmc-medium, locuteur « pierre » (`sid = 1`)** | H | 22,05 kHz | 0,12 s | 0,37 s (2 threads) | CC-BY-SA 4.0 |
| tom-medium | H | 44,1 kHz | 0,30 s | 1,31 s (2 threads) | AGPLv3, ~10 dB plus faible |
| siwis-medium | F | 22,05 kHz | 0,05 s | 0,21 s | CC-BY 4.0 |

**Retenu : `vits-piper-fr_FR-upmc-medium`, locuteur 1 (« pierre »), 2 threads**, version normale (pas `-int8`, bien plus lente ici). Archive : `https://github.com/k2-fsa/sherpa-onnx/releases/download/tts-models/vits-piper-fr_FR-upmc-medium.tar.bz2` (80 Mo), extraite dans `~/.local/share/jarvis/models/vits-piper-fr_FR-upmc-medium/`. Échantillons à écouter : `scratchpad/tts/wavs/`.

**API (sherpa-onnx 2.0.1) :** `OfflineTts::create(&OfflineTtsConfig { model: OfflineTtsModelConfig { vits: OfflineTtsVitsModelConfig { model, tokens, noise_scale: 0.667, noise_scale_w: 0.8, length_scale: 1.0, .. }, num_threads: 2, .. }, .. })` → `Option<OfflineTts>` (`Send + Sync`) ; `tts.generate_with_config(text, &GenerationConfig { speed, sid: 1, phoneme_codepoints, .. }, None)` → `GeneratedAudio` (`samples() -> &[f32]`, `sample_rate()`).

**Piège :** sherpa-onnx 2.0 n'embarque plus espeak-ng : pour une voix Piper, le texte doit d'abord être converti en phonèmes avec la crate **`piper-phonemize` 1.5.9** (GPL-3.0, espeak-ng embarqué, ~0,3 ms par phrase), puis passé en `phoneme_codepoints` avec un texte vide (modèle : exemple amont `vits_tts_phonemize.rs`). **Vérifié** (essai isolé, 3 tours dans le même processus, y compris sous `MALLOC_CHECK_=3`) : `piper-phonemize = "1.5.9"` en liaison statique par défaut cohabite avec whisper-rs (statique) et sherpa `shared`, sans nouvelle bibliothèque `.so` ni changement du `build.rs`. Binaire : +8 Mo (données espeak-ng embarquées). Au premier appel, ces données sont décompressées dans `$TMPDIR` ; on les place plutôt dans `~/.local/share/jarvis/espeak-ng-data/` avec `piper_phonemize::initialize(dir)`. La première compilation télécharge la bibliothèque et les données (réseau nécessaire). Code qui marche :

```rust
let ph = piper_phonemize::phonemize(text, "fr")?;
let cps: Vec<Vec<i32>> = (0..ph.num_sentences()).map(|k| ph.get_phonemes(k).unwrap_or_default()).collect();
let g = sherpa_onnx::GenerationConfig { sid: 1, speed, phoneme_codepoints: Some(cps), ..Default::default() };
let out = tts.generate_with_config("", &g, None::<fn(&[f32], f32) -> bool>)?; // out.samples(), out.sample_rate()
```

Jarvis est un projet personnel : la GPL de piper-phonemize ne pose pas de problème.

**Lecture :** sortie `cpal` de l'oreille, ouverte à la configuration par défaut du périphérique (ici 48 kHz stéréo) ; rééchantillonnage 22 050 → 48 000 et passage en stéréo en Rust ; coupure par un `AtomicBool` lu dans le callback (silence en ~10-20 ms). Bips générés directement à la fréquence du périphérique.
